### T6 — [P2] Required route parity fixtures can become empty while their focused tests pass

Primary: [ios/RailKit/Tests/RailCoreTests/RouteHintsParityTests.swift:107–125](/Users/sager/Documents/GitHub/JTM-iOS-App/ios/RailKit/Tests/RailCoreTests/RouteHintsParityTests.swift:107), especially the unguarded outer and inner fixture loops at 108 and 110. Corresponding cases: [RouteSolverParityTests.swift:129–198](/Users/sager/Documents/GitHub/JTM-iOS-App/ios/RailKit/Tests/RailCoreTests/RouteSolverParityTests.swift:129) and [RouteStationCandidatesParityTests.swift:81–118](/Users/sager/Documents/GitHub/JTM-iOS-App/ios/RailKit/Tests/RailCoreTests/RouteStationCandidatesParityTests.swift:81).

Scenario: fixture maintenance replaces a valid decoded fixture's `cases` with `[]`, or removes one region and its test rows. The hint test, edge-rule test, Dijkstra fixture test and station-candidate test all return success without asserting that the required region/case corpus survived. With top-level `cases: []`, they never call the relevant production function or execute any expectation. For route hints, retaining the two region records but emptying each nested `cases` also produces a complete green result without exercising hint construction or attempts. Non-fixture Dijkstra regressions remain useful, but cannot establish the missing cross-language parity contract.

Evidence: `PortFixtures.decode` simply JSON-decodes the requested type; existence and syntax checks do not reject a valid empty array. The three committed fixtures currently contain `mo` and `hk`: route-hints has 4 rows per region, route-solver-core has 7 rows per region, route-station-candidates has 6 probes per region (targeted read-only JSON query). The route-hints builder at `app/scripts/build/port-fixtures/route-hints.mjs:76–112` collects sections from the first three trains and skips unresolved endpoints, so a source/sample change can remove all nested probes without invalid JSON. Its contract at 115–121 requires deriving the same constraints for shipped train sections. The common builder's render at `app/scripts/build/build-port-fixtures.mjs:364–366` reports array length and serializes; it supplies no population assertion. Current verification policy retires automatic regeneration checks, so a native focused test must defend its own required evidence inputs.

Action: require the declared `mo`/`hk` fixture region set and usable nonempty nested probes/cases before entering these existing test loops; preserve intentional negative solver results. Keep expected values in the independent committed JS fixture. This is a narrow improvement to existing regressions, not a request for a corpus campaign or replacement runner. No current fixture is claimed missing/empty; the finding is the proved false-pass path when its required evidence contracts shrink.

### T7 — [P3] One UI drag adds the application's origin twice

Primary: [ios/RailMapUITests/WorkspaceEditingTests.swift:394–398](/Users/sager/Documents/GitHub/JTM-iOS-App/ios/RailMapUITests/WorkspaceEditingTests.swift:394).

`revealServiceField` constructs the app's zero-normalized coordinate, then adds absolute `cell.frame.midX/midY` as its relative offset. A nonzero application frame therefore shifts the intended native cell gesture by `app.frame.minX/minY`; the gesture can hit a different control or outside the Form and the test's subsequent progress assertion fails without establishing a product regression. Its stated cell-anchoring contract is contradicted by that coordinate arithmetic.

The correct existing same-file helper at 775–779 subtracts the app frame origin before applying the offset; `EditorUITestSupport.tap` at 835–840 does the same. Reuse that conversion or start from a cell-local normalized coordinate. This is test portability under a nonzero origin, not a demonstrated failure in the usual zero-origin simulator configuration. No current native origin, failure rate or runtime flake was measured, so P3 is appropriate.

- Conventional SwiftPM discovery is correctly declared in [ios/RailKit/Package.swift](/Users/sager/Documents/GitHub/JTM-iOS-App/ios/RailKit/Package.swift) for RailCoreTests. - Package header/loop tests include literal format cases and independent packaged identities. The compiled-graph and StrokeRide index tests compare optimized paths with exhaustive/public paths, which is meaningful equivalence coverage; it does not independently certify the source geography or shared algorithms.
- PhysicalTopologyRoutingTests, PhysicalSectionContinuityTests, KandaSelectedEndpointTrimTests and RailValidity/RailHistoryTests exercise actual public graph/solve/certification interfaces with literal physical connection, identity, half-open date, snap, cancellation, cache and historical contracts. Real-data regressions require their selected station/line/junction inputs and fail if they disappear. No new shared-state race was established in these files. Saved JS answers intentionally represent cross-language agreement, as documented in the builder header, not an independent geographic/source verdict. - Railway editing tests exercise authored/generated visit protection, repeated occurrences, payload preservation, metadata round trips, undo conflict detection and retained outer sections through the actual editing interface. They provide useful depth at an existing seam instead of mocking internal helpers.
- TimetableAppFlowTests and TrainTimetableDatabaseTests use production read-only SQLite queries, drafts, service dates and import/export paths. Its report distinguishes unavailable/partial/complete, known failures and uncertain optional-stop order. Successful execution would not mean all routes are correct. Translation persistence relaunches with the same ID. Native helper geometry is reviewed statically only; mounted accessibility row counts in long-detail tests do not alone prove total SwiftUI instantiation or rendering performance. BasemapRenderingTests does sample screenshots for texture/black blocks in bounded waits and keeps orientation cleanup; no pixel verdict follows until that focused native test is actually run.
