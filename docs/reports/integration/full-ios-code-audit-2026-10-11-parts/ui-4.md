### UI4-1 — [P2] Detail pairs one station's name with another station's time and platform

Primary: [/Users/sager/Documents/GitHub/JTM-iOS-App/ios/RailMap/Journeys/RideDetailView.swift:359](/Users/sager/Documents/GitHub/JTM-iOS-App/ios/RailMap/Journeys/RideDetailView.swift:359) (also 372–377, 406–432, 983–984).

Scenario: a valid recorded train has A(false, departure 08:00, platform 1), B(true, departure 08:30, platform 2), C(true, arrival 09:00), with canonical origin A and destination C. Open the separate journey information/detail surface. Its departure block displays A with B's 08:30 departure and platform 2; VoiceOver combines that incorrect station/time/platform pair too. If the final recorded stops are unmarked, the arrival block similarly gives the canonical destination another station's arrival/platform. This requires no async interleaving.

Evidence: stationPairCard sends `name: train.origin`, `code: train.originStationCode`, but `stop: firstRiddenStop`; the destination does the equivalent. stationSummary derives time/platform from that supplied stop and the displayed name/code independently. firstRiddenStop/lastRiddenStop search raw `rideSegment` flags, while the existing canonical boundary rule in Statistics.swift:1867–1885 also excludes pass-through stations and evaluates inherited ride state. The four-language/timezone helper does not reconcile those identities. RideCard.swift:157–167 uses the first/last recorded stop times with the corresponding canonical endpoints, so the separate detail and selected card also disagree in this scenario. Existing editor/import schemas permit partial rider markings; this is not a malformed record claim.

Action: create a single endpoint value containing the station identity, time and platform. Either present the full recorded endpoint pair consistently, or intentionally present effectively ridden stopping boundaries with all fields taken from those same boundary stops. Do not mix canonical endpoint names with rider-filtered timing; if ridden boundaries are selected, use the existing shared effective-stop rule.

Test gap: LongJourneyDetailUITests.swift covers lazy long lists and snapshot refresh, not partly ridden endpoint identity/timing. Add one focused valid partial-ride detail assertion checking both the visual and combined accessibility station/time/platform pair; include a pass-through raw-flag case when adopting ridden boundaries. No tests run.

### UI4-2 — [P2] Railway guide geometry bypasses the selected MapKit datum

Primary: [/Users/sager/Documents/GitHub/JTM-iOS-App/ios/RailMap/JourneyEditor/RailwayRouteGuideView.swift:581](/Users/sager/Documents/GitHub/JTM-iOS-App/ios/RailMap/JourneyEditor/RailwayRouteGuideView.swift:581) (also 585–588, 689–723).

Scenario: AppleMapDatum's persisted probe verdict contains tw, hk, mo or kr for a device served a GCJ-02 basemap; open a railway route comparison/repair guide for a journey in that region. The ordinary map's network, rides and station geometry use the adopted display datum, while every guide polyline, choice marker and endpoint uses the package's WGS84 coordinates directly. Thus the guide and ordinary map submit inconsistent coordinates for the same physical subject on that same device/service. This is a source-level conditional inconsistency, not a claimed measured alignment offset or a new geographic verdict.

Evidence: RailwayGuideGeometry converts interval/station coordinates directly into CLLocationCoordinate2D and retains no country/datum context. RailwayGuideMap passes those values directly to MapPolyline/Annotation. CompactPackage.swift:17 supplies the country, and EditorRoutePackageCache.swift:17–28 loads canonical per-region packages unchanged. RideEditorView.swift:799–816 loads `Region.resolved(draft)`; routeGuideSheet:507 is not Japan-only, and workspace card repair:655 passes its guide package. In contrast RiddenRouteStore.DrawnSegment.init:103 and RailNetworkStore.swift:1189,1401,1609,1714 explicitly call AppleMapDatum.display. AppleMapDatum.swift:25–84 makes the transform conditional on the applied persisted scope, so global-service WGS84/Japan cases mask the defect. ADR 0004's shared WGS84/MapKit presentation rule supports applying the same existing probe decision, not reintroducing an unconditional country shift.

Action: apply `AppleMapDatum.display(..., country: package.country)` once when building the guide's MapKit presentation geometry for both interval vertices and stations. Leave canonical package/choice/source values unchanged. Geometry fingerprints should describe the resulting display geometry so any redraw identity remains coherent.

Test gap: RailwayRouteEntryUITests.swift:96–105 seeds only jp and checks opening/cancellation/choice selection; it never checks guide coordinates under a nonempty adopted datum scope. A focused geometry assertion with a candidate-country package and an explicit nonempty display scope should compare guide vertices/endpoints to the same production transform, and confirm the WGS84 case remains canonical. No tests run.

## Architecture judgments, separate from correctness findings

- **RailMapCoordinator's lifecycle interfaces hide real depth.** update/tearDown and the MapKit delegate interface centralize deferred gesture/playback work, geometry request identity, publication fencing, overlays, label collision and selection. Detached preparation and main-actor materialization cross an intentional seam; cancellation reaches the worker and the publication ID is checked again after materialization/yield (1051–1113). Matching has an independent revision and line content/dependency identity (2951–3055). These are useful owners; preserve their interface invariants rather than exposing private helpers to split the 4,233-line file.
- **Geometry/marker/cache ownership has an opportunity for greater locality.** Coordinator captures LineInputs, geometry frame identity and marker contexts; MapLineGeometry, MapNetworkGeometryCache and MapStationLabelCoordinator each own a part of the implementation. Callers must know which changes invalidate which owner. If changing this behavior, a complete prepared-frame module could accept one immutable input and own the matching/cache/publication plan behind a narrow interface. This is a concrete in-process seam with existing worker and MapKit materialization adapters, not a request for a new speculative generic cache layer. No measured performance benefit is asserted.
- **RideDetail's station-summary seam is too shallow.** The caller separately supplies name, code and Stop plus role; that interface requires knowledge that those inputs represent the same station, and no implementation enforces it. UI4-1 demonstrates lost locality. An endpoint value module can encapsulate full-record versus ridden-boundary selection and return a coherent identity/time/platform/accessibility result; both card/detail are real consumers.
- **RailwayGuideGeometry is useful projection depth with one missing interface invariant.** It hides interval lookup, choice/shared-run matching, fingerprints, bounds and endpoint projection behind one value. Its caller should not need separate datum knowledge; owning presentation conversion in this existing module fixes UI4-2 once and preserves canonical data outside the MapKit seam.
- **WorkspaceDerived is a deliberate cache owner.** Its retained Array keys make buffer-identity comparison valid for immutable value inputs, while dates/regions/query/naming/scope keys express semantic dependencies. No measured rendering-speed claim follows from this review. Closure-driven filtering still requires callers to supply a matching scopeKey; do not add another ad hoc view cache.
