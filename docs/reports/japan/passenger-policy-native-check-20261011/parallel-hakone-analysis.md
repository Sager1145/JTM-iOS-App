## 源/渲染证据边界

- 现有修复 builder `repair-hakone-passenger-corridor.mjs:39` 起检查 OSM way 的铁路/公司/非 service/非货运条件、相邻节点与同序测绘支撑点；`:95` 起要求 stem 单次绘制及三个精确 fork 端点。它们证明保存的图结构约束，不能证明具体时刻列车平台分配。
- 当前 JS `app/public/rail-stroke.js:1865` 与 Swift `ios/RailKit/Sources/RailCore/Rendering/ContinuousStroke.swift:709` 仅在同方向精确共线、非硬拐点邻域且非锚点时删支撑点。当前图的反向短曲线仍存在；没有依据建议恢复像素容差删点。
- 当前 capture-state 的 sampled `smoothToDisplayMaximumMetres` 为约 0.28–0.81m；这是单向 smooth→display 最近线采样，不是 Apple 像素或地理误差。003418 5–9、003419 0–6 存在 capped sampling，因此不能宣称全点误差上界。较大的红蓝分离与源位置/参考差异一致，但具体归因仍需同腿对应证据。
- GSI 保存 GeoJSON 有 209 个 railway features，包含 `orgGILvl`、`ftCode`、`railState`、tile，至少部分 `featureID` 为 null。保存 receipts 的 datasetAsOf 为 2026-07-01；不能据此断言每条线测绘日期。最近铁路或局部多条 GSI 线也不自动等于选定客运主腿。
- Inspector 当前比较为完整线 DisplayParts 的独立中心线裁切，`ownLane=0`、`mainLane=0`，没有主产品公司平行线/family 合成。图片里旁边的蓝线是苹果原有铁路，不能计作第二条 JTM 客运显示线。

## 可修复项与停点

本证据足以排除“为了贴苹果，把真实小弯抹掉或删折返 stem”的修复方向。没有足够独立定位证据支持立即移动任一长段。最小可执行下一步是为出山南侧道岔来路、上大平台西侧长接近段、宮ノ下南侧紧弯各建立一条明确的 OSM/GSI 同腿对应记录；优先复用保存 GSI，只在对应无法分辨时补一个局部独立定位。证明同腿与位置后才做局部显示几何/接缝修复，保持物理站点与里程，重拍一个受影响视点。

不要求补全货场、存车线或每根平台股道。客运折返必经的代表 stem 属于本次范围。未发现本任务可以无新增证据立即修复的生产几何项；全线、时刻平台分配、公司合成、像素残差均未在本次证明。
