## 结论

`005352` 是两条线路共用的同一个物理须ヶ口站记录，不是同名异站，也不需要新建物理连接。当前源数据已经把名古屋本线 #17 的末三点与津岛线 #0 的前三点编码成严格反向的同一段进路；该共享段在站场西北侧离开实际分岔后，津岛线继续向西，名古屋本线继续向丸ノ内方向。

若修复须ヶ口附近显示，最小联动范围是三个完整区间：名古屋本线 #17、#18 和津岛线 #0。两条线路必须使用完全相同的 `005352` 显示站点坐标；名古屋本线 #17 与津岛线 #0 的至少三点反向共享干必须保持逐点相同，不能把它们各自拉成在站点处相交的 V，也不能用 `displayBranchLeadIns` 另造连接。

新 z18 原图支持另一个明确结论：津岛线 #0 从画面西缘至共享干前的西北弯段，当前青/红中心线持续位于自身黑色双轨的南侧，偏差随曲率变化，并非只延长端点即可修复。因而 #0 必须按完整区间复核和拟合。原图不支持把站点移到大块蓝色站房/站区外框的几何中心；标签、填充和站内多轨遮挡了精确站台面边界，现有证据尚不足以给出替代坐标。

## 现有显示机制

Web 端先将 `displayStationCoordinates` 和 `displayIntervalCoordinates` 仅应用于显示副本，然后解码区间并把两端焊接到显示站点；锚点重建会将相邻进路平滑回站点。相关实现见：

- `app/public/rail-network.js:773`：`anchorIntervalsToStations`
- `app/public/rail-network.js:864`：`displayLineForCoordinates`
- `app/public/rail-network.js:879`：`decodeIntervals`，两端由站表覆盖
- `app/public/rail-network.js:1363`：明确显示坐标不改变物理区间身份
- `app/public/rail-network.js:1399`：锚定前识别严格共享轨道；共享点数至少为 3
- `app/public/rail-network.js:1411`：用同一共享开关约束显示重建

Swift 端使用同一契约：

- `ios/RailKit/Sources/RailCore/Data/CompactPackage.swift:89`：显示站点、显示区间和显示支线引入字段是独立显示数据
- `ios/RailKit/Sources/RailCore/Data/CompactPackage.swift:98`：`displayCoordinate` / `displayStations`
- `ios/RailKit/Sources/RailCore/Data/CompactPackage.swift:196`：解码显示覆盖
- `ios/RailKit/Sources/RailCore/Data/CompactPackage.swift:244`：物理解码由站表覆盖区间端点
- `ios/RailKit/Sources/RailCore/Data/CompactPackage.swift:290`：显示区间覆盖后再次焊接到显示站点
- `ios/RailKit/Sources/RailCore/Rendering/DisplayParts.swift:1272`：锚定前记录至少三点的精确共享开关，随后用显示站点重建

因此，后续若形成有证据的候选，应满足：

1. 两条线路的 `displayStationCoordinates["005352"]` 必须字节级相同。
2. 名古屋本线 #17 和津岛线 #0 的共享干控制点必须完全反向一致，至少保留当前三点共享条件。
3. 津岛线 #0 用完整 `displayIntervalCoordinates[0]` 拟合自己的黑轨；名古屋本线 #17 若共享干被调整，也必须以完整 #17 同步更新。
4. 名古屋本线 #18 必须作为同一站点的完整相邻区间复核，确保锚点重建没有站内尖角、回头或切轨。即使 #18 的主体无需新控制点，也不能只检查端点截图。
5. 不应为这里添加 `displayBranchLeadIns`：共享轨道和分岔已由原始区间编码。支线引入会重复画轨或掩盖共享开关约束。
