## Platform geometry

The owning implementation is `ios/auxiliary/RailAlignmentInspector/InspectionKit/Sources/RailInspection/AppleMapPlatformExtractor.swift`.

- Lines 36–46 threshold every unmasked pixel independently. The actual thin-platform RGB `(104,128,178)` passes all tests: red 104 ≥75, blue−green 50 ≥28, blue−red 74 ≥45, and 50 >1.5×24. Exact broad-casing RGB `(65,89,136)` fails red ≥75. Consequently, the proposed Fujinami extension toward `(330,490)` and broad Shobata casing from approximately `(320,405)` to `(806,158)` are **not explained by admitting that exact casing colour in the current production filter**. They are erroneous static picks unless separate pixel evidence supports them; changing the filter to include that casing would worsen the error.
- Lines 50–65 use four-neighbour connected components. The source never joins separate components by colour or equal length. Lines 66–92 fit each qualifying component independently using its PCA tangent, longitudinal/transverse projections, and physical size/aspect gates. The parent observed two Fujinami components: 1,641 pixels, bbox `(445,253)`–`(549,360)`, and 1,438 pixels, bbox `(461,272)`–`(566,376)`. At Shobata the two own faces are unequal: 1,733 pixels, bbox `(402,251)`–`(627,382)`, and 1,676 pixels, bbox `(393,194)`–`(696,364)`. These bboxes are component evidence, not oriented endpoints. Do not substitute a shared length or the casing's larger bbox.
- Concrete geometry limitation: lines 85–88 deliberately use the 2nd and 98th percentiles of *all component pixels*. This necessarily drops some real end pixels, including a tapered face tip; it is not a procedure for identifying only antialiasing or specks. Lines 97–100 therefore return a fitted, trimmed cartographic axis and box, not known physical endpoints. The midpoint is the average of those fitted longitudinal bounds on the transverse centreline, not the area centroid; this is already the correct kind of oriented long midpoint once the bounds are trustworthy.
- Concrete completeness limitation: lines 123–130 can resolve any size-qualified component when its midpoint has one unambiguous local rail match and it does not touch an OCR mask. A naturally missing-fill fragment can therefore receive `platform_cartography_midpoint_candidate` without proof that both ends represent the full visible face. Mask-created fragments are explicitly unresolved, and edge-touching components are discarded (lines 58, 66), but there is no general endpoint/completeness flag. This is a source capability limit, **not a demonstrated casing/component mistake in the supplied Tsushima captures**.
- Lines 104–114 project the fitted midpoint orthogonally onto each accepted rail segment, admitting segments up to 25° from the face axis and offsets ≤8 m, with the foot restricted to the segment interior. This is perpendicular to the rail segment, not exactly along the fitted face normal when their directions differ. Lines 120–153 preserve ambiguity for competing nearby bands/groups. No railway or station identity is resolved here.

The analysis caller in `ios/auxiliary/RailAlignmentInspector/Sources/AppleMapAnalysisService.swift:153–162` uses platform axes only as search windows, then obtains independent **physical rail glyph** runs, even when the ordinary analysis is in transit-cartography mode. `AppleMapRailExtractor.swift:135–160` requires paired narrow dark valleys with brighter interior/exterior at four longitudinal probes; `:233–250` requires persistence and splits unsupported runs. Roads/building edges are not a nearest-track fallback. These safeguards must remain.

The export already calls the frame `unassigned_cartographic_platform_frame_not_survey` (`AppleMapAnalysisService.swift:72–76`) and says no source geometry writes (`:97`). It carries the selected `lineID` and `intervalIndex` as context; these fields must not be mistaken for identity proof. It exports axis pixels and fitted midpoint (`:59–68`) but does not export an explicit complete-extent or identity-resolution flag.

### Small improvement justified by the source

Keep each verified narrow-fill component separate, including unequal faces. Return the existing fitted axis as a candidate alongside separate endpoint/extent evidence. If both visible narrow-face termini have actually been established, retain their longitudinal bounds rather than labelling the percentile-trimmed box a full frame; compute the midpoint from those bounds. If either terminus is clipped, masked, missing, or unverified, set an explicit extent-unresolved flag and do not promote that fragment midpoint to a station coordinate. A connected-pixel extreme alone is not proof of a physical terminus.

For a requested **face-normal** rail projection, intersect the line through that oriented midpoint along the face normal with a locally supported glyph segment, requiring the intersection to lie within the segment and the established offset bound. Preserve all rival-band checks and return no resolved rail point when the intersection/support is ambiguous. Do not use an untyped nearest track. Independently export `stationIdentityResolved: false` and `passengerGroupIdentityResolved: false` until identity is explicitly reviewed; a geometric glyph match alone cannot make either true. This is a bounded improvement to candidate reporting/projection, not permission to merge components or change passenger-group geometry.

## Terminal station same-view export

The no-op has an exact state-owner explanation:

1. `InspectorModel.swift:86–88` gets `currentInput` from `lineID#stationIndex`. For a non-loop line, `makeInputs` normally creates `stationCount−1` interval inputs (`:500–506`). At the last station there is no input for its station index.
2. The on-screen same-view evidence button uses only line/busy/mode conditions (`InspectorApp.swift:164–165`), so it appears enabled at the terminal. Its action calls `captureRequested`.
3. `captureRequested` silently returns when `currentInput == nil` (`InspectorModel.swift:301–306`). The menu/Option-Command-S path correctly has that same input requirement in its enabled state (`InspectorApp.swift:331`, `:462–464`), so the shortcut cannot initiate capture either.
4. The downstream capture path already supports a viewport without an interval: it takes optional `currentItem?.id` (`InspectorMap.swift:159–181`), `InspectionEvidence.capture` accepts optional `itemID` (`InspectionEvidence.swift:61–69`), and `viewRecord` writes station/camera context while including interval input only when present (`InspectorModel.swift:521–538`). `recordEvidenceSuccess` retains the bundle but skips interval-review association if itemID is nil (`:354–356`). No synthetic interval is needed.

Small fix for the requested terminal viewport export: centralize a `canCaptureEvidence` predicate based on selected line, busy state, and non-extracted mode; use it in the button, command bridge, and `captureRequested`, allowing nil interval input. Retain optional itemID behavior, and label the result station/viewport evidence so it never certifies an interval. Merely changing the visible button to disabled would cure misleading UI but would not satisfy terminal station export. The prior interval's detailed last-view export succeeds because that interval input exists.

Source-only conclusion: the terminal export failure is explained; the frame extractor has real trimmed-end/completeness/projection limitations, but it already rejects the supplied exact casing colour and separates connected components. No evidence here establishes a production broad-casing misclassification or a correct station coordinate.
